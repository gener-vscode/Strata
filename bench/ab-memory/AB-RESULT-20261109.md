Both sides are the same model (`Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS`), the same pack (`Strata-data/packs/iq3_xxs`), the same tokenizer, the same MTP directory, one GPU, `--resident-budget-gib 37`, `--vram-reserve-mib 512`, `--conversation-cache-mib 0`, `--max-context 128000`, `--kv q4_0`.

## 2. Why

**The fork pins the resident copy; the upstream config does not.** `strata-iq3_xxs.json` has `"STRATA_RESIDENT_PIN": "0"`, and the two logs say it plainly:

```
fork:      FileExpertSource: allocating 36.50 GiB page-locked cache complement
fork:      mapped pinned cache complement ready: resident 36.50 GiB, pinned 36.50 GiB in 86 s
upstream:  FileExpertSource: allocating 30.38 GiB pageable resident cache complement
upstream:  pageable resident cache complement ready: resident 30.38 GiB, pinned 0.00 GiB in 54 s
```

Both read the same `RAM budget 37.00 GiB`, and the same `--resident-budget-gib 37` is in both configs (`rdna3/configs/iq3_xxs-1gpu.json:69` and `strata-iq3_xxs.json:25`). The difference is how the budget is committed:

- Page-locked bytes are handed to the driver and cannot be reclaimed or swapped. `MemAvailable` drops by the whole 36.5 GiB and stays down.
- Pageable bytes stay in the normal page cache. The kernel can drop or swap them, so `MemAvailable` sits 5.8 GiB higher even though the engine's RSS is 32 GiB.

That is most of what "the fork uses far more memory" looks like from the outside: less available RAM, more of it charged to one process, and the fork's last exit cost 45.3 GiB peak with 3.3 GiB of swap.

Two further terms follow from the same choice, both visible in the logs:

1. **The pinned path spends more of the budget on the prompt path.** The fork keeps all 6041 lend slots in RAM (`9.73 GiB of the budget's remaining 10.74 GiB`); upstream keeps 2097 (`3.37 GiB of the remaining 9.99 GiB`). Same budget, different split.
2. **The fork's GPU cache is bigger, so the card ends fuller.** The upstream engine reserves more before filling the cache — `512 MiB reserved (+184 MiB for the draft head, +256 MiB for what is allocated after the cache)` — the fork reserves `512 MiB (+105 MiB for the draft head)` with no room left for what comes after. The fork then sits at 414 MiB free, below its own `--vram-reserve-mib 512`, and prints the #2065 warning that at that point amdgpu pages GPU memory into system RAM. Upstream ends at 714 MiB free and prints no warning. That is a code difference between the trees, not a config difference.

## 3. The rest of the config gap (not the memory term, but it is why "same config" is not exact)

| | fork | upstream |
|---|---|---|
| engine env | 45 `STRATA_*` variables | 2 (`STRATA_HIPBLASLT_TUNING`, `STRATA_RESIDENT_PIN`) |
| hipBLASLt tuning file | `gfx1100-hipblaslt-100200.txt`, runtime is 100202 → log says "version mismatch … using hipBLASEx", table unused | `gfx1100-hipblaslt-100202.txt` → matches the runtime |
| extra args | `--mtp-draft-vocab rdna3/draft_vocab_zh60k.bin` | `--ple-gguf <shard 00002>`, `--control-vector-scaled …:1.0`, `--control-vector-layer-range 4 44`, `--cvec-mode project`, `--cvec-dir per-layer` |
| config keys | `gpu`, `layer_split`, `sampling`, `engine_silence_s` | none of those |

All 25 engine flags in either config are understood by both parsers. `--ple-gguf` and the control-vector flags make the upstream run load a different set of tensors, and the fork's tuning table is refused — both can move buffer sizes, but neither is 6 GiB.

Also: `--pool-workers 8` on 8 physical cores makes the upstream engine warn ("8 CPU expert workers … Recommended: --pool-workers 7"), the fork's tree does not warn. Speed only, not memory.

## 4. Next two runs, one variable each

These are the two that close the question. Everything else stays as it is now.

```sh

```

If TEST 1 moves the fork down to ~32.5 GiB and TEST 2 moves upstream up to ~38.5 GiB, the whole difference is `STRATA_RESIDENT_PIN` and the fork's code is not at fault for host RAM. What would still be left is the VRAM side: 414 MiB free against 714 MiB, which is the engine's own cache-reserve rule differing between the trees. TEST 3 for that: `--vram-reserve-mib 1024` in the fork config and compare `vram_used_kB` and the expert cache slots.

## 5. What was not tested

No same-prompts benchmark was run; both snapshots are idle-time readings of two live services about 15 minutes into their runs, so each RSS includes whatever working buffers that traffic built up. The engines are different builds (`fb975936515c` vs `b062453c1e38`) from trees that do not share git objects (`ce61f3b0` vs `93b82f47`), so "the same code, one flag changed" is not what this comparison proves — TEST 1 and TEST 2 are what would prove it. Section 2's second point (the cache-reserve rule) is read from the two logs and the two source trees, not from a controlled run: unconfirmed static analysis.
