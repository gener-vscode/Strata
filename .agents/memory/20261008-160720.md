## Knowledge/quantified answers already delivered (do not re-derive)
1. Trade-offs of enabling vision: +0.9 GB mmproj download; +`strata-vision` helper build (10-20 min if self-built); GPU path reserves ~1.4 GB VRAM ⇒ expert slots shrink ⇒ Q2_0 541→531 prompt / 90.7→86.9 output tok/s, IQ2_XS 468→458 / 77.1→74.0, IQ3_XXS 411→401 / 64.7→59.5. **`--vision` alone costs zero tokens** — slowdown is only from the reservation. CPU path costs nothing on the GPU.
2. **7800X3D iGPU cannot be a second CUDA device**: `cuda_device` maps to CUDA device numbering (only exists on the cuda backend); AMD has no GPU image encoder (`hip_vision()` → images off; `--vision gpu` silently turns images off; Windows AMD has no CPU encoder either); gfx1036 unsupported; also only 2 CU, no dedicated VRAM. Real options: idle NVIDIA card + `"vision":{"cuda_device":N}` with `--vram-reserve-mib 700` (#408), or CPU path (keeps expert cache intact).
3. **Image token math: 1 image token = 32×32 px** (14×14 patch − spatial merge 2). tokens ≈ round(w/32) × round(h/32); verified against docs (640×480 → 20×15 = 300) and against measurements. 300 → 640×480 native, or 1080p downscaled to ~736×416. 768 → 1152×640. 1024 → 1344×768. 2048 measured → 1980 tok. Oversized images are resized preserving aspect (mtmd smart_resize), never an error. `max_tokens` is **per picture**, and counts into context/KV; identical pictures are encoded once, so only distinct pictures each consume budget. mtmd/log warns Qwen-VL grounding wants ≥1024 tokens (`load_hparams`, 640/642).
4. **User-run benchmark I performed** with their own helper + mmproj (2560×1440 test image `docs/media/runpagoda.png`, `--threads 8`, server running): 300 cap → 276 tok (23×12), 3.7 s; 768 → 720 tok (36×20), 22.2 s; 1024 → 1008 tok (42×24), 41.6 s; 1536 → 1508 tok, 90.5 s; 2048 → 1980 tok, 151.6 s. **Scaling is super-linear (ViT attention), not proportional.** Threads sweep at 720 tok (warm): 8 → 21.7 s, 12 → 19.8 s (+9.7%), 16 → 17.0 s (+21.6%); cold at 1024: 8 → 41.2, 12 → 37.4, 16 → 31.6 s. So 16 threads ≈ 100% CPU util, worth ~20%, no VRAM/expert-cache effect. The dashboard's constant ~49-51% CPU = 8 threads on 16 logical CPUs (`setup.py` default `cpu_count//2` = 8).
5. Q8_0 mmproj: 590 MiB vs BF16 865 MiB (encoder RAM −~280 MiB), quality loss negligible (cosine 0.997-0.999 max 0.9995), **encode time identical within 3% for ≥768 tokens** → it saves RAM, not time. Docs recommend it for `--vision cpu`. Create with `llama-quantize <bf16 mmproj> … Q8_0`.
6. `--vision` engine-side footprint is only the mrope image-position table (max_context+64)×3×int32 = ~1.9 MB at 160K context; multi-GPU OK (each card keeps its own table). Without `--vision` in engine args: `ERR this engine was starting without --vision` (generate.cpp 1705/8081/2637). Unsloth UD-Q4_K_XL has no vision (`"vision": False`). AMD/HIP vision = CPU only, Linux only (#606). Lazy-load text-only configs refuse vision configs. `--vram-reserve-mib 0` allowed (validation ≥0; setup only warns for gpu) but not recommended when GPU is shared with desktop.
7. Hand-editing the JSON instead of `--setup` is fine and preserves user's args; `--setup` rewrites `args` (docs/INSTALL.md warns hand-made engine options are not carried over) though it preserves user-added vision keys (image_max/image_min_tokens/threads/temperature) and a pre-existing mmproj key. Only `threads`/`max_tokens` re-run risk: setup writes its own defaults for SETUP_VISION keys.
