## 背景（承接上一轮 compact 的 Strata 结论）
- 环境：Strata（/home/tommy/repo/Strata, commit c4bc29f）后端为 vendored llama.cpp（`llamacpp/llama/llama-0624`，build 78543）。用户 machine 用 `--no-mmproj --n-gpu-layers 99 --max-context 160000 --flash-attn on --mlock --priority idle --threads 6 --ctx-checkpoints 4 --kv-split --kv-resident 32768`。
- 已确认：`--no-mmproj` 只是不加载 vision tower；有图片请求时 C++ 会抛 `mmproj not initialized`，并 `ggml_backend_device_select(... ggml_backend_dev_type(...) GGML_BACKEND_DEVICE_TYPE_GPU)` → CPU 回退 = 全量 offload 慢路径。
- `--mmproj` 加载 + GPU 常驻 ≈ +0.6–1.0 tok/s；context 32768→65536 ≈ −2 tok/s。
- Vision token 标定（llama.cpp VisionEncoder: `image_size/32` × `image_size/32` × 4）：512×512→256 tok（实测 372）、1080p→1008 tok（实测 1096）、19×19→1 tok、9855×790→1981 tok（实测 2065）。

## 本轮问题：「旧 session 后续 payload 无图」vs「每 turn 都有图」矛盾
**结论：两边观察都正确，但机制不同。**

1. **每 turn 都有图 = 边界之后**：用户 debugger 观察到每个 sent request 都带图 → 对应 `openai-format.ts:166-182`，确实以 `image_url: data:image/png;base64,…` 送出。所以「我读不到旧截图」不等于「payload 无图」。
2. **边界之前永久移除 = compact 硬切**：`buildApiRequestContext.ts:337-341`（`fromLastValidCompact`）→ `slice(lastCompactIdx + 1)`，最后一个 compact pair 之前（含该 pair）完全不进入 prompt；`getAllMessages()` 本身完整（`task/fork.ts:141`，`context = [oldHistory, newHistory]`），裁剪只发生在 build 阶段。用户旧 session 最后有 `[Context Window Safey Net]` compact，`api_requests.log`（300 行）grep `type":"image"` = **0 命中**（该 log 只记录 truncated 段，边界之前 9855 那张未出现，不可判定）。
3. 第二个失图机制：`textifyContext()` 的 `content.filter(c => c.type === 'text')`（`:103`）在 tool_use/tool_result 配对失败时（`:184-186`）会把 pair 内所有非 text block 丢掉，`preserveBinary=true` 救不到。
4. 其他删除路径：`trimOldHistory`（`MIN_KEEP_COUNT=20`，仅 `clearTask()` 与 `Task.clearHistory()` 使用）、`stripEmptyMessages`、`stripUnresolvedContentBlocks`、`fitContextWindow` / `extractKeyContext`（只 retain COMPACT/WRITE_FILE/EDIT_FILE/ASK/PRESENT_PROPOSAL/ATTEMPT）、`fitContextWindow` 由中间删（`mid=floor(len/2)`）。
5. **新发现（缺陷）**：`shared/utils/token-counter.ts:261-305` 的 `estimateTokens()` 先执行 `stripBinaryContent()`，`type==='image'` → `return undefined`，即 Gener 把图片当 **0 token**；而实际每张 512² ≈ 256 tok、1080p ≈ 1008 tok。这使 overflow gate 系统性低估，解释「估算未爆但 provider 已爆」（本次 metrics 13815→34720→…→87671，profile `max_input_tokens: 128000`）。

## Compact 决策（已回答）
**主动 /compact，不要等自然 overflow。** 理由：
- 图片在两种路径都会消失（compact 硬切 / overflow 裁剪），所以为「保图」拖延无收益。
- 主动 compact：可控损失（我写的纯文字 summary 会进入新 context）。被动 overflow：不可控损失（live pair 变 `[Context Window Safey Net]` 截断 YAML，污染后续所有 turn）。
- Compact 前若有任何图片内容尚未写成文字（secret code、数值、截图内报错），应先 harvest 成文字再 compact。
